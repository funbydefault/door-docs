FunByDefault · Customer guide

Door 1.0

Swing and slide door motion you can configure and control in the Unreal Editor and Blueprints. No C++ knowledge is required for setup or integration.

Editor and Blueprint quickstart

Prerequisites: install Door for the engine and platform attached to your download. Start with a Blueprint project and a level where you can see the door.

  1. Open Edit > Plugins, enable Door, and restart Unreal if prompted.
  2. Open Window > Place Actors. Search for Door Showcase Swing Actor and drag it into your level. It already contains a root, hinge, panel, and Swing Door component with matching tags.
  3. Select the actor. In Details, select its Door Panel component to replace the mesh or materials. Select Swing Door to adjust Swing Angle, Open Time, and Close Time. Keep the default settings for this first test.
  4. Keep the actor selected and open the Level Blueprint from the Blueprints toolbar menu. Right-click in the graph and choose Create a Reference for the selected door. Drag from that reference, add Get Component by Class, and set its class to Swing Door Component.
  5. Drag from the returned component and add Open Door. Connect Event BeginPlay through a Delay of two seconds to Open Door. Compile, save, and press Play.

Expected result: the panel swings 90 degrees around its hinge over one second. To test closing, connect another Delay and Close Door after the opening request.

Tip: use Door Showcase Slide Actor for a paired sliding door. Its native defaults are Dual mode, Y axis, and 105 cm of travel per panel. Get its Slide Door Component in the graph instead.
Multiplayer: this quickstart is a standalone test. In a networked game, only the server may change a door's state. Follow the Blueprint request flow before connecting client input.

Add Door to your own actor

  1. Open your actor Blueprint. Add a Swing Door Component or Slide Door Component from the Components panel.
  2. Set the moving mesh or hinge to Movable. For a swing door, add a Scene Component at the hinge and attach the panel mesh to it. Offset the mesh so its edge meets the hinge.
  3. Select the moving component and expand Tags in Details. Add the required entry under Component Tags: SwingDoor for a swing hinge, SlideDoor for one slider, or DoorLeft and DoorRight on separate dual panels. Actor Tags are a different field.
  4. Select the Door component and set its mode, axis, travel, and timing. Each configured tag must identify exactly one scene component. A dual door needs two distinct components.
  5. Drag the Door component into your Blueprint graph as a reference. Call Open Door, Close Door, or Toggle Door from your own gameplay. Compile and save the Blueprint, place an instance, and test it.

Use the same component reference for a trigger overlap, a switch, a quest event, or your interaction system. Door supplies motion; your game decides when to request it. Route mouse and keyboard, gamepad, and touch actions through your game's input layer to the same door action.

You can also create a Blueprint subclass of either supplied door actor and edit its components. Save the Blueprint and reopen the project to check that your settings and closed layout remain as authored.

Configure a swing door

Swing Component Tag identifies the panel or hinge that rotates. It defaults to SwingDoor. Place that component at the hinge edge; Door uses its authored pivot and does not infer a hinge.

Swing Angle is the rotation from closed to fully open, in degrees. The component default is 90 degrees. A negative angle reverses direction. Choose Z for the usual vertical hinge.

The supplied swing actor tags its Swing Hinge and attaches Door Panel below it. Move the hinge to the desired edge, then move or resize the child panel relative to the hinge. Tag the hinge only, so the target stays unique.

Changing the layout during play: fully close the door, change its hinge layout, angle, axis, or tag, then call Refresh Swing Target From Current Layout. The current relative rotation becomes the new closed rotation. A refresh while open or moving is ignored.

Configure a slide door

Single

Set Slide Mode to Single. Give one panel the SlideDoor Component Tag. Door adds the signed Slide Distance along the selected local axis.

Dual

Set Slide Mode to Dual. Tag separate panels DoorLeft and DoorRight. Positive distance moves the left panel against the axis and the right panel along it.

The component defaults to Single mode and 200 cm travel. Details accepts distances from -1000 to 1000 cm. Reverse the sign to reverse a single panel or swap dual directions. Zero leaves the panels in place.

For Single mode on the supplied slide actor, select its Slide Door component and change the mode to Single. Its left panel already has SlideDoor. The right mesh stops moving; hide it or repurpose it as a fixed track. If you hide it only during play, also disable its collision when it should not block the doorway.

Hide at the open endpoint

Hide Slide Components When Fully Open is off by default. When enabled, the resolved panels and their attached scene components hide at the fully open endpoint. Closing restores each component's captured Visible and Hidden In Game flags. Hiding does not disable collision.

Use Set Hide Slide Components When Fully Open when changing this option during play. Disabling it restores the captured visibility immediately.

Changing the layout during play: fully close the door, create or move its panels into their intended closed layout, then call Refresh Slide Targets From Current Layout. This captures locations and visibility again. Refreshes while open or moving are ignored.

Blueprint controls and queries

NodeBehavior
Open DoorStarts opening or reverses a closing door. A request while already Open or Opening has no effect.
Close DoorStarts closing or reverses an opening door. A request while already Closed or Closing has no effect.
Toggle DoorOpens from Closed or Closing; closes from Open or Opening.
Set Door Open ImmediateSnaps to Open or Closed. Open selects the endpoint. Broadcast Local Change controls this instance's event and audio.
Is Door Open / Is Door ClosedChecks the stable endpoint state.
Is Door OperatingChecks Opening or Closing. A client may wait in this state at the visual endpoint until the server's final update arrives.
Get Door Open AlphaReturns the local open amount: 0 is closed, 1 is open, and intermediate values are partial movement.

The normal sequence is Closed → Opening → Open → Closing → Closed. A reversal starts from the current open amount. A half-open door with a one-second full close time takes about half a second to close.

For startup or saved-state restoration, call Set Door Open Immediate after the target components are ready. Set Broadcast Local Change to false when this instance should skip the transition event and audio. Remote clients that receive a changed replicated state still process their normal event and audio.

Use the control nodes: writing state or alpha separately does not synchronize the motion, visuals, and network state. Use the immediate node to reset, and the open or close nodes to animate.

React to a state change

  1. Drag your Door component reference into the graph and add Bind Event to On Door State Changed.
  2. Create the matching event with Previous State and New State inputs.
  3. Use New State to branch for your response, such as updating a light, playing your own effect, or scheduling a close request.

Door updates its state, open amount, motion status, and visuals before broadcasting the event. Before handlers run for Open, the panel is at the open endpoint and Is Door Operating is false on that instance.

A server-side handler can call Open Door, Close Door, or Set Door Open Immediate to start the next action. Door keeps that new action instead of overwriting it after the callback returns.

Note: event inputs describe the transition that triggered the callback. If another handler has already requested a later action, a query may return a newer state. Use Previous State and New State to identify the event you are handling. Avoid creating an endless chain of immediate state changes.

Clients receive local events when replicated state changes arrive. Very short or rapidly reversed transitions can be skipped between network updates. Use a separate replicated gameplay event if your game must deliver every intermediate action.

Networking and authority

The server controls door state. The component replicates a motion description: state, start time, duration, starting open amount, and target open amount. Clients apply the panel transforms locally using server world time.

The component replicates by default. Both supplied door actors have replication enabled. On your own actor, leave Auto Enable Owner Replication enabled, or enable Replicates in its Blueprint Class Defaults. Keep door actors relevant to the clients that need to see them.

Blueprint client request flow

  1. In your player-owned Character or Player Controller Blueprint, create a Custom Event such as Request Door Open. Add a door actor input. Set Replicates to Run on Server, and enable Reliable for an occasional interaction request.
  2. Call that event from your local input or interaction logic. Use the same flow for mouse and keyboard, gamepad, and touch.
  3. On the server, validate the request using your game's rules: actor validity, distance, access, and any line-of-sight requirement.
  4. After validation, get the target's Swing or Slide Door component and call Open Door, Close Door, or Toggle Door. Other clients receive the resulting motion state.
Local interaction
    → Run on Server event on the player's owned actor
    → Server validates the target and access
    → Door component action
    → Replicated motion on relevant clients
Ownership matters: a shared world door is usually not owned by the client. Put the request event on the player's owned actor. Calling a door control directly on a client is rejected; Door does not provide the request RPC or authorize an interactor.

Configuration must match

Tags, mode, distance, angle, audio, visibility policy, and target layout are configuration, not replicated Door state. Author matching settings on all instances. If you change them during play, your game must distribute the configuration and apply it everywhere before refreshing the fully closed layout.

Clients can reconstruct an in-progress operation from its timing when it becomes relevant. Dedicated servers skip audio. These implementation paths do not establish acceptance for every network setup.

Verification status: release-specific multiplayer acceptance is still pending for this staged guide. Listen-server and dedicated-server modes, late join, reconnect, ownership changes, and latency or packet-loss behavior need exact-package verification before a support claim is published.

Assign optional audio

Select the Door component and expand Door Sound Settings. Empty slots are silent. Assign your own compatible Unreal sound assets.

SlotWhen it plays
Trigger Sound / Opening Start SoundThe state changes to Opening. If both are assigned, both play.
Opening Loop SoundWhile opening. Choose an asset configured to loop.
Fully Open SoundThe state changes to Open.
Closing Start SoundThe state changes to Closing.
Closing Loop SoundWhile closing. Choose an asset configured to loop.
Fully Closed SoundThe state changes to Closed.

Movement loops stop when motion finishes, reverses, or the component ends play. Audio attaches to the resolved panel or hinge when available, otherwise to the owner's root. Dedicated servers create no Door audio. Door supplies sound hooks and includes no audio assets.

Expose Gameplay Tags

Select the Door component and expand Gameplay Tag Settings. Choose your project's Static Tags and optional Closed, Opening, Open, and Closing tags. Call Get Door Gameplay Tags to collect the static tags plus the tag for the current state.

These are Gameplay Tags used to query state. They are separate from the Component Tags that identify moving panels. Door does not register a required Gameplay Tag hierarchy, add tags to an ability system, or require GameplayAbilities.

Create custom motion in Blueprint

  1. Create a Blueprint class. Under All Classes, choose Door Component Base as the parent.
  2. Implement the Apply Door Open Alpha event. Its Open Alpha input runs from 0, fully closed, to 1, fully open.
  3. Use the alpha to drive your own scene-component transforms or material parameters. You can remap it for eased motion.
  4. Add that component Blueprint to your actor and use the same door control nodes.

Door already owns timing and reversal, so avoid starting another Timeline for each alpha update. The base component has no built-in panel movement until you implement this event. Built-in Swing and Slide components use their own native motion.

Included contents

  • Door Component Base: shared timing, states, networking, audio hooks, events, and Gameplay Tag queries.
  • Swing Door Component: rotation of one tagged panel or hinge.
  • Slide Door Component: single or paired panel movement and optional open-endpoint hiding.
  • Door Showcase Swing Actor and Door Showcase Slide Actor: editable native starting points for your own door Blueprints.
  • Door Example Game Mode: a timer-driven harness that discovers Door components and toggles them on the server.
  • DoorShowcase: the plugin-owned example map at /Door/Maps/DoorShowcase.
  • Full native source: optional inspection and extension.

The motion components tick only while Opening or Closing and resolve targets when play begins or a refresh is requested. The native door actors and example Game Mode have no actor Tick.

Diagnostics and troubleshooting

During Play In Editor, inspect the Door component's Door State, Current Open Alpha, and resolved Swing or Slide targets in Details. Open Window > Developer Tools > Output Log and filter for LogDoor or your actor's name.

The door will not open
Check that the moving mesh or hinge is Movable. Check Component Tags on scene components, not Actor Tags. Each configured tag must match exactly one component; dual panels must be distinct. Missing, duplicate, or overlapping targets produce a warning and reject opening. Fix the tags, reset fully closed, and call the matching refresh node.
The state changes but the panel stays still
Check the resolved target, axis, and travel. Zero distance or angle leaves the panel in place. In a custom Door Component Base Blueprint, implement Apply Door Open Alpha. A component with no custom visual implementation still updates its state.
The swing panel rotates around its center
Use a hinge Scene Component and attach the panel below it with an offset. Tag the hinge only. The supplied swing actor already has this structure.
A client action is ignored
Route the request through a Run on Server event on the player's owned actor, validate it there, and call the Door component on the server. Client-authority warnings can be enabled in non-Shipping builds; they are compiled out in Shipping.
Different clients show different motion
Check actor replication and relevance, then compare mode, axis, angle, distance, tags, and closed layout on every instance. Door replicates motion state, not runtime configuration. Test a server request rather than a direct client call.
A changed panel moves from its old layout
Fully close the door before replacing or moving panels. Rebuild them in their closed layout and call Refresh Swing Target From Current Layout or Refresh Slide Targets From Current Layout. A refresh while open or moving is ignored.
An open hidden slider still blocks the doorway
The hide option changes visibility only. Adjust your panel collision or have your gameplay change collision when that is required. Door has no obstruction solver.
A panel's authored visibility is not restored
Close the door, set the intended Visible and Hidden In Game flags on the panel and its children, and refresh the slide targets. At runtime, use the hide-option setter so disabling it restores captured flags immediately.
A callback starts the next motion unexpectedly
Check every On Door State Changed handler. Event inputs identify the original transition, while state queries may reflect an action requested by an earlier handler. Filter by New State and avoid unbounded immediate open/close callbacks.
A movement loop keeps playing
Door stops its own loop at endpoints, reversals, and EndPlay. Check that another gameplay system is not starting the same sound. Assign a looping-capable asset to loop slots.
Gameplay Tags are empty
Choose Static and state tags in Gameplay Tag Settings. Component Tags used for panel targeting do not become Gameplay Tags automatically.

Migration

Existing components and panel tags

The reflected swing and slide class, enum, property, and control names are retained. Earlier internal builds could choose the first component when tags were ambiguous. Door now rejects ambiguous targets. Audit existing actors so each configured tag identifies exactly one component and dual panels are distinct, then refresh the closed layout and retest.

Example map path

The map has moved from /Door/Maps/DoorExample to /Door/Maps/DoorShowcase. The plugin supplies package and object redirects for the old map and its built-data paths. Use the new path for new references; verify existing references after upgrading.

Restore state through the API

Use Set Door Open Immediate rather than assigning DoorState or CurrentOpenAlpha independently. Version 1.0 has no plugin-owned SaveGame format. Your project decides what to save and restores that state through the control node on the server.

Older native subclasses

If a source subclass uses the early UpdateDoorOperation hook, move its transform logic to ApplyDoorOpenAlpha. Door owns normalized timing, reversal, endpoints, and replicated state.

Public API policy

Public Blueprint names, C++ symbols, serialized enum and property names, and config keys are compatibility surfaces. A public symbol is deprecated for at least one published release before removal, with guidance and redirects where needed. Future save-data or config-schema changes require a versioned migration path and regression coverage.

Scope and compatibility

Door supplies swing, single-slide, and dual-slide motion; endpoint controls; state events and queries; optional sound hooks; Gameplay Tag exposure; and server-controlled replicated motion state.

Your game supplies input mappings, interaction UI, locks and access rules, client request RPCs, prediction, save persistence, and any navigation or obstruction policy. Door uses transform animation rather than a physics hinge. It includes no audio assets or complete interaction framework.

Compatibility status: this is a staged release guide. The current supported engine and platform matrix has not yet been certified for publication. Use only combinations verified for the exact release and attached to its Fab download; this guide does not establish an untested compatibility claim.

Optional C++ reference

The editor and Blueprint paths above are sufficient for setup and gameplay integration. Use this reference only when extending native code.

Module and component

Add Door to your module dependencies and include the component header you use.

#include "SlideDoorComponent.h"

SlideDoor = CreateDefaultSubobject<USlideDoorComponent>(TEXT("SlideDoor"));
SlideDoor->SlideMode = ESlideDoorMode::Dual;
SlideDoor->MovementAxis = EDoorMovementAxis::Y;
SlideDoor->SlideDistance = 160.0f;
SlideDoor->OpenTime = 0.8f;
SlideDoor->CloseTime = 1.0f;

Add movable scene components with unique DoorLeft and DoorRight tags. Call controls from server-authoritative gameplay.

Replace generated panels

SlideDoor->SetDoorOpenImmediate(false, false);
// Place replacement panels in their closed layout.
SlideDoor->RefreshSlideTargetsFromCurrentLayout();

Native custom motion

Derive from UDoorComponentBase and override ApplyDoorOpenAlpha(float OpenAlpha). For tag queries, use GetOwnedGameplayTags. For callbacks, bind a reflected handler with the signature void HandleDoorStateChanged(EDoorState PreviousState, EDoorState NewState) to OnDoorStateChanged.
